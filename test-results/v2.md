# Test run v2: rooms, duplicate bookings, cancel and reschedule, redelivered events

Date: 2026-11-03 · n8n 2.44.4 (self-hosted, Docker) · Model: Claude Haiku 5.5 · 24 tests, 41 messages

"Now" is fixed at 2026-11-03 (Tue) 15:00 Asia/Taipei, as in v1.

## 1. What changed

| Feature | How |
|---|---|
| Room availability | 3 demo rooms: A and B (up to 8 people), the big room (up to 20). Each booking holds a room for 2 hours. `Decide` picks the smallest free room that fits. If none is free, it suggests up to 3 free start times on the same day, closest to the requested time. |
| Duplicate bookings | A customer who already has a booking on the same day with an overlapping time gets a reminder instead of a second booking. |
| Cancel and reschedule | `Decide` finds the customer's upcoming bookings (one: use it; several: list them and ask for a number; cancel with a date: match by date). Nothing changes until the customer answers "確定". Cancel sets `已取消`; reschedule checks rooms again, sets `待確認`, and notifies the store. Room availability is checked a second time at confirmation. |
| Redelivered events | `Check Event` looks up `webhookEventId` in a new `line_events` table. Seen before: skip. New: record it, then continue. |
| Short yes/no answers | While a confirmation is pending, replies such as 好, 對, 確定, 不用了 are matched by code, without relying on the model's intent label. |
| Prompt | New intents `cancel`, `change`, `confirm`, `deny`; new field `pick` for "choose number 2". |
| Question reply | Now includes the bookable hours (11:00 to 21:00). |
| Order of the last steps | Reply to the customer first, then push to the store (see live test, problem 2). |

New tests T18 to T24 (20 messages); T17 now expects "no booking found" instead of a generic cancel reply. T06 also checks that 12 people get the big room. A seed step books all three rooms at 11/12 19:00 before the run, for T19.

## 5. Live LINE test (v1 workflow, before these changes)

Phone → LINE official account → Cloudflare quick tunnel → n8n on my PC.

Problem 1: the first three messages were dropped at `Check Signature`. The execution log showed LINE's signature did not match the one computed with the stored Channel secret. A signed request sent through the same tunnel with a known test secret matched, so the tunnel did not change the body. Re-entering the Channel secret fixed it.

Problem 2: the first complete booking was saved, but the customer got no reply. The store notification ran before the reply and failed with LINE error 400 "Failed to send messages": the store user ID came from a channel under another provider, and LINE user IDs differ between providers. Fix: use the user ID this channel sees, and reply to the customer before notifying the store.

## 6. One execution at a time

n8n was recreated with `N8N_CONCURRENCY_PRODUCTION_LIMIT=1` (Docker Compose, same data volume).
Checked with a temporary workflow (webhook that answers at once, then waits 5 s), deleted afterwards:

| Test | Result |
|---|---|
| Two requests at the same time | First answered in 70 ms. Second waited: its execution started 0.01 s after the first one ended, and its 200 came back after 5.1 s |
| Second request gives up after 2 s (like LINE's timeout) | The queued execution still ran, right after the first one |

LINE counts a webhook that gets no response within 2 seconds as `request_timeout`. With this setting, a message that waits behind another one can show up as a timeout in LINE's webhook statistics, but it is still processed and answered in order.
