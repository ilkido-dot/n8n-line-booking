# Test run v4: the customer chooses the room size

Date: 2026-11-04 · n8n 2.44.4 (self-hosted, Docker) · Model: Claude Haiku 5.5 · 39 tests, 76 messages

"Now" is fixed at 2026-11-03 (Tue) 15:00 Asia/Taipei, as in earlier versions. This version also ships the v3 changes ([v3.md](v3.md)).

## 1. What changed

| Feature | How |
|---|---|
| Room size | Until v3, `Decide` gave every booking the smallest free room that fit, so 4 people always got a small room. Now, once the five fields pass and there is no duplicate booking, `Decide` asks 小包廂 or 大包廂 (`ask_room`). The question lists the booking details and the room text from `store_info` (capacity and minimum spend), and offers only sizes that are free at that time. |
| When the program decides | More than 8 people (small rooms seat 8): large room, and the reply says why (「小包廂最多 8 位，12 位幫您排大包廂。」). Customer says 都可以: the smaller size that is free. |
| One size left | Only that size is offered; a short 「好」 books it. |
| Requested size taken | Other size free: ask whether to switch, and list free times for the requested size (`room_type_full`). If the customer then gives another time, the requested size is kept. Neither size free: suggest times for the requested size (`room_full`). |
| Reschedule and switching size | A change keeps the booking's size unless the customer names one (「可以改成大包廂嗎」). More than 8 people after a change switches to the large room, with a note. `pending_room` now stores the size; drafts written by v2 (room ID) still work. Confirmations and store pushes now show the room, and say 「變更」 instead of 「改期」. |
| Prompt | New field `room_type` (`small`, `large`, `any` or null): filled only when the customer names a size, never from the number of people. The prompt also lists the customer's upcoming bookings (date, time, people), see section 3. |
| Data | `booking_drafts` has a new column `room_type`. |
| Check Answer | Every listed dish and performer must appear word for word in the answer (the v3 run 3 failure). |

Tests:

## 3. The T39 failure

Message 2 of T39 is 「可以改成大包廂嗎」, sent right after the small-room booking was created. In run 99 the model labelled it `booking` with `room_type: large`, so `Decide` started a new draft (「目前記下：包廂：大包廂」, then asked for a date) instead of proposing the change, and message 3 「確定」 had nothing to confirm. In runs 97 and 98 the same message was labelled `change`.

The prompt showed the booking in progress (none here) and the last question, but nothing about bookings the customer already had. Without that, "change my booking to the large room" and "I'm booking and want the large room" look the same. Fix: `Prepare` adds the customer's upcoming bookings (up to 3; date, time, people) to the prompt, and the `change` rule says that with an existing booking and no booking in progress, 「改成…」「換成…」「改到…」 is a change. Input grew from 2,356 to 2,448 tokens per call.

## 4. How the model read room sizes

In all six full runs (97 to 99, 101 to 103), the model filled `room_type` on exactly the 21 messages where the customer named a size (小包廂, 大包廂, 都可以) and on no other message: not for 12 people (T06), and not for 「大包廂可以坐幾個人？」 (T34).

「好」 in T37 was labelled `other` every time. `Decide` matches short replies itself, so it still booked the small room.

## Known limits

- The room-size flow has not been tested on a phone yet; only with the simulated messages above.
- A reschedule keeps the booking's size. When that size is full at the new time, it suggests other times but does not offer the other size (the customer can still say 「改成大包廂」).
- Room sizes and capacities are settings in `Decide`; the minimum spend shown in the question comes from `store_info`. Changing rooms means changing both.
